# Product

## Platform

web

## Stack

Electron desktop app (Windows, macOS, Linux). The renderer is web tech: React 19, TypeScript, Tailwind, Zustand, built with electron-vite. Mockups are plain HTML/JS in `mockup/`, generated by `mockup/build.py` from `mockup/src/*.dc.html`. Stack details live in `docs/PRD-mission-control-hermes.md` §8.

## Users

People who run a Nous Research Hermes Agent on their own Linux VPS, usually with several profiles (agents) behind one multiplex gateway. They are technical: comfortable with SSH and a terminal, and they check on their agents several times a day, on a desktop, often with the app left open on a second screen. Their jobs: see at a glance which agents are alive and working, read what an agent did and what it cost, talk to an agent, adjust its model, soul and memory, and catch failures (a cron job that errored, a gateway that died) before a human notices.

## Product Purpose

Hermes Agent Mission Control is one realtime control room for a Hermes install, reached over SSH. It shows agent status, server load, cron jobs, a live feed of agent activity including thinking, a graph of the Obsidian vault used as second brain, a 1-on-1 chat, and per-agent settings. Planned for v1.1: session history and search, token and cost analytics, tool-call inspection, log and gateway views, cron control, a skills browser, a memory-change timeline, and a command palette. Success is that any stock Hermes user can connect with only SSH credentials and trust what the screen says.

## Positioning

It works against any stock Hermes install with zero changes to the VPS: nothing installed, no helper files written, no ports opened, no sudo, no Hermes source or plugin changes. The collector is a Python script piped through stdin to Hermes' own interpreter, so nothing is left on the server's disk. A web dashboard or a plugin cannot truthfully claim that.

## Operating Context

Single user, one VPS per window, one saved SSH connection that auto-connects on launch. Data comes from read-only access to `state.db`, `cron/jobs.json`, logs, gateway state and `/proc`, plus the official `hermes` CLI for chat and for the few writes. The UI language is English; the people who build and spec it write in Indonesian.

## Capabilities and Constraints

- Zero-Change is non-negotiable (PRD §3.2). Writes happen only on an explicit user action (Save, Send, Restart, Upload, Pause, or something typed in the terminal), go through the official `hermes` CLI where one exists, show a diff and a confirmation first, and are logged locally without their contents.
- Never read `.env`, `auth.json` or API key values. Writing a key with `hermes config set` is allowed; reading it back is not.
- Never add `--yolo` or bypass Hermes' approval policy.
- Every remote command is built from individually quoted arguments, never string concatenation.
- Agent and vault markdown is untrusted and must be sanitized.
- Fits one window with no page scrollbar on the dashboard; long panels scroll inside themselves. Text zoom 70 to 150 percent.
- Undecided: multi-VPS support and multi-agent chat rooms (deferred to a later cycle). Exact Hermes subcommands for skills, cron control and gateway control are to be verified against the Hermes v0.21.x docs before they are specified.

## Brand Commitments

Name: Hermes Agent Mission Control. The user explicitly chose the "hacker view" look: terminal and btop style panels with titles on the border, the Dracula palette, JetBrains Mono for the whole UI, VT323 only for screen titles and big numbers. The logo and app icon are the HMAC block-letter mark in `assets/brand/` (green `#50FA7B` on `#21222C`); do not redraw it in a font. Dracula's Comment color (`#6272A4`) is decoration only because it fails text contrast. These are binding constraints, not suggestions.

## Evidence on Hand

PRD v0.9+ (`docs/PRD-mission-control-hermes.md`), a set of interactive HTML mockups with sample data, and a published design canvas (PRD §6.9). No real users, no production data, no usage numbers. Future work must not invent any.

## Product Principles

1. Read first, write rarely. Anything that changes the VPS is deliberate, previewed as a diff, and reversible where possible.
2. Say what is known. Show stale, unavailable or unsupported states honestly, with the age of the data, never a confident blank.
3. One glance, then depth. The dashboard answers "is everything fine?"; each detail screen answers one question well and links to its neighbours.
4. Dense but calm. Operators want many facts at once; hierarchy, alignment and restraint keep it scannable.
5. Never touch secrets. The app does not read or display credentials or environment values.

## Accessibility & Inclusion

Text contrast at least 4.5:1. Status is never conveyed by color alone (label or icon too). Keyboard-first with visible focus. Reduce-motion option and `prefers-reduced-motion` respected. Text size adjustable from 70 to 150 percent.
