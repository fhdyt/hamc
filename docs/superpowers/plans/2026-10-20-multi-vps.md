# Multi-VPS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Save several Hermes servers and switch the one connected server from the status bar, Settings → Servers or the palette.

**Architecture:** `connections` becomes a real list. `SettingsStore` holds the active connection id, so every existing `getConnection()` caller follows the active server. `MissionSession` resolves the row of a connect request, sets it active before the attempt and resets per-server memory when the id changes. The renderer gets a server list in `useConn`, a `switchServer` action that reuses the Launch screen, a status bar menu, a Servers tab and palette items.

**Tech Stack:** Electron, better-sqlite3, zod, React 19, Zustand, Vitest, Playwright for Electron.

**Spec:** `docs/superpowers/specs/2026-10-20-multi-vps-design.md`

## Global Constraints

- Zero-Change: switching only opens and closes SSH sessions; nothing is written on any VPS.
- UI strings are English; Dracula tokens; secondary text `#A9B2D3` / `#8B95BD`.
- A label is at most 40 characters, no control characters; empty shows `user@host`.
- Secrets never leave main and are never logged; `app.log` gets `server switch <id>` / `server forget <id>` only.
- Every remote command still goes through `buildCommand` (no new remote command in this plan).
